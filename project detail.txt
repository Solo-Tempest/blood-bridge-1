1. PROJECT OVERVIEW
================================================================================

Blood Bridge is a full-stack web platform that automates the connection between
blood donors and hospitals during medical emergencies. The core problem it solves
is that existing blood-donation processes rely heavily on manual phone calls,
WhatsApp groups, and word-of-mouth — all of which are slow and unreliable during
genuine emergencies.

PROBLEM STATEMENT:
  - Hospitals waste critical time calling people one by one to find donors.
  - Donors have no structured way to receive emergency alerts.
  - There is no proximity-based, automated system that matches blood type,
    distance, and eligibility in real time.

SOLUTION:
  Blood Bridge automates the entire flow:
    1. Donors register with their location, blood type, and health details.
    2. A hospital raises a blood request from their dashboard.
    3. The system instantly finds all compatible, eligible, nearby donors.
    4. Those donors receive an email notification with request details.
    5. If not enough donors respond within a time window, the system
       automatically expands the search radius (escalation).
    6. Donors accept or decline from their portal; hospitals see real-time
       status including accepted donors' contact details and map location.

3. SYSTEM ARCHITECTURE
================================================================================

The system follows a standard 3-tier architecture:

  [Browser / React Frontend]  <-->  [Spring Boot REST API Backend]  <-->  [PostgreSQL DB]
                                              |
                                       [Gmail SMTP]
                                    (emails sent async)

KEY ARCHITECTURAL DECISIONS:
  - Stateless REST API: No server-side sessions. Every request is authenticated
    with a JWT Bearer token passed in the Authorization header.
  - Role-based access: Three roles (DONOR, HOSPITAL, ADMIN) stored as an enum
    in the users table. Spring Security enforces role checks via JWT claims.
  - Async donor matching: When a hospital creates a request, the donor search
    runs in a separate thread (@Async) so the API response returns immediately.
  - Scheduled escalation: A background job (@Scheduled, every 5 minutes)
    checks all active requests and widens the search radius if needed.
  - Privacy-first design: Hospital contact phone numbers are only revealed to
    a donor AFTER they accept the request. Hospital name and address are also
    hidden until acceptance.
  - No Redux / no global state manager: Frontend uses React hooks + localStorage
    (keys: bb_token, bb_user) for all state management.
  - CORS configured for localhost:5173 (Vite dev server).

7. CORE ALGORITHMS & BUSINESS LOGIC
================================================================================

------------------------------------------------------------
7.1 BLOOD TYPE COMPATIBILITY MAP
------------------------------------------------------------
The DonorMatchingService maintains a static map of who can donate to whom:

  O-  can donate to:  O-
  O+  can donate to:  O-, O+
  A-  can donate to:  O-, A-
  A+  can donate to:  O-, O+, A-, A+
  B-  can donate to:  O-, B-
  B+  can donate to:  O-, O+, B-, B+
  AB- can donate to:  O-, A-, B-, AB-
  AB+ can donate to:  ALL groups (universal recipient)

------------------------------------------------------------
7.2 DONOR ELIGIBILITY RULES
------------------------------------------------------------
A donor is eligible for matching if ALL of the following are true:
  1. is_available = true
  2. Age is between 18 and 65 years (calculated from dateOfBirth)
  3. Weight >= 50 kg (if provided)
  4. Last donation date is more than 90 days ago (or donor has never donated)

------------------------------------------------------------
7.3 HAVERSINE DISTANCE FORMULA
------------------------------------------------------------
Used to compute straight-line distance (in km) between the hospital
and each donor using their GPS coordinates (latitude, longitude).

  a = sin²(Δlat/2) + cos(lat1) × cos(lat2) × sin²(Δlon/2)
  distance = 2 × R × atan2(√a, √(1−a))     where R = 6371 km

This is computed for every candidate donor during matching, and again
when the hospital fetches the donor list (sorted closest first).

------------------------------------------------------------
7.4 ESCALATION SYSTEM (Automatic Radius Expansion)
------------------------------------------------------------
When a blood request is created, the initial search radius is 5 km.
If enough donors do not accept within a time threshold, the system
automatically expands the search radius.

  Escalation Level 1 : Radius =  5 km  (initial)
  Escalation Level 2 : Radius = 20 km
  Escalation Level 3 : Radius = citywide (no limit)

Escalation triggers (minutes since request was created):
  URGENT requests : Level 1→2 at 10 min, Level 2→3 at 20 min
  NORMAL requests : Level 1→2 at 15 min, Level 2→3 at 30 min
  CRITICAL requests: Starts at Level 3 (citywide) immediately, no escalation.

The EscalationService @Scheduled job runs every 5 minutes:
  - Fetches all ACTIVE, non-CRITICAL requests with escalation_level < 3
    and accepted < donors_needed
  - Calculates how many minutes old each request is
  - If threshold reached, increments escalation_level, saves, and triggers
    a new round of DonorMatchingService.matchAndNotify()
  - The DonorNotificationRepository deduplication check
    (existsByDonorAndBloodRequest) ensures already-notified donors are
    NOT notified again when the radius widens.

------------------------------------------------------------
7.5 OTP SECURITY SYSTEM
------------------------------------------------------------
Two separate OTP flows:
  A) Pre-registration OTP: Verifies email ownership before account creation.
     No user record needed — purely validates the email.
  B) Login OTP: Verifies registered users by sending a code to their
     existing registered email.

Security controls:
  - Rate limiting: Max 3 OTP requests per 10-minute window per email.
  - Expiry: OTP is valid for 5 minutes only.
  - Attempt limit: Max 5 wrong attempts before OTP is locked.
  - Single-use: OTP is marked used=true immediately on success.
  - Invalidation: Sending a new OTP invalidates all previous valid OTPs
    for that email (sets used=true on all).
  - Random generation: 6-digit code from Java SecureRandom
    (not Math.random — cryptographically safe).

------------------------------------------------------------
7.6 JWT AUTHENTICATION FLOW
------------------------------------------------------------
  1. User logs in (password or OTP) → server validates credentials.
  2. Server generates JWT signed with HS256 and a base64-encoded secret.
     Token payload: subject = user email, expiry = 24 hours.
  3. Token returned to client, stored in localStorage (key: bb_token).
  4. Every subsequent API request: client adds header
     "Authorization: Bearer <token>"
  5. JwtAuthFilter (OncePerRequestFilter) intercepts all requests,
     extracts and validates the token, loads the user from DB, and
     sets the SecurityContext — so Spring Security knows who is calling.
  6. All endpoints except /api/auth/** require a valid JWT.

------------------------------------------------------------
7.7 PRIVACY & DATA REVEAL RULES
------------------------------------------------------------
Hospital contact phones (contactPhone1, contactPhone2):
  - NEVER shown to donor while notification is PENDING or DECLINED.
  - Revealed in DonorNotificationResponse only when status = ACCEPTED.

Hospital identity (name, street, area):
  - Hidden while PENDING.
  - Revealed only after donor ACCEPTS.

Hospital GPS coordinates (lat, lng):
  - Always visible to donor (used to show map even before accepting,
    so donor can estimate distance and decide whether to accept).

Donor details shown to hospital:
  - For PENDING/DECLINED: name, blood group, city, distance, status badge.
  - For ACCEPTED: full details — phone, date of birth, weight,
    last donation date, total donations, lat/lng (for map link).

10. FCM PUSH NOTIFICATIONS
================================================================================

Blood Bridge integrates Firebase Cloud Messaging (FCM) to deliver real-time
push notifications to donors the moment a compatible blood request is created,
without relying on the 30-second polling cycle alone.

INTEGRATION:
  - Firebase SDK configured in frontend/src/firebase.js.
  - When a donor logs in, the browser requests notification permission and
    the FCM service worker registers a device token.
  - The device token is sent to the backend and stored against the donor's
    profile so the server can target that specific device.
  - When DonorMatchingService finds a matching donor, it triggers both:
      a) An email notification (via SmsService / Gmail SMTP)
      b) An FCM push notification to the donor's registered device token.
  - The push notification appears instantly on the donor's device even
    when the Blood Bridge tab is not open.

NOTIFICATION CONTENT:
  - Title: "Blood Bridge — Urgent Request" (or "CRITICAL Blood Needed!")
  - Body: Blood group, units, approximate distance, urgency level.
  - On notification tap: opens the Donor Portal Donation Requests tab
    directly so the donor can respond immediately.

BENEFIT:
  Without FCM, donors only see new requests when they open the app or when
  the 30-second auto-refresh fires. With FCM, the alert is instant — critical
  in a life-or-death blood emergency.

11. ML-BASED DONOR RANKING
================================================================================

Blood Bridge includes a Python-based machine learning microservice that ranks
candidate donors before notifications are sent, ensuring the most eligible and
reliable donors are contacted first.

ARCHITECTURE:
  - Implemented as a separate Python FastAPI microservice.
  - The Spring Boot backend calls this microservice via HTTP after the initial
    candidate list is assembled (compatible blood group + eligibility rules).
  - Returns a ranked list with a score per donor.
  - DonorMatchingService uses this ranked order to determine notification priority.

ML PIPELINE:
  Phase 1 — Rule-based Elimination:
    Hard filters that disqualify a donor before ML scoring:
      - Age < 18 or > 65 years
      - Weight < 50 kg
      - Last donation < 90 days ago
      - Marked as unavailable

  Phase 2 — ML Eligibility / Health Score:
    A scikit-learn model scores each eligible donor on:
      - Time since last donation (longer = higher score)
      - Total donations history (experienced donors ranked higher)
      - Proximity to hospital (closer = higher score)
      - Donor availability consistency over time

  Phase 3 — Priority Ranking:
    Donors are sorted by combined score (descending). The top-ranked donors
    receive notifications first, maximizing the chance of a quick response.

TECHNOLOGY:
  - Language    : Python 3
  - Framework   : FastAPI
  - ML Library  : scikit-learn
  - Model type  : Rule-based scoring + weighted ranking model
  - Endpoint    : POST /rank-donors  (receives candidate list, returns ranked list)

BENEFIT:
  Without ML ranking, all eligible nearby donors are notified at once in
  arbitrary order. With ranking, donors most likely to respond quickly and
  donate safely are prioritized — reducing the time to find a match.

12. SECURITY IMPLEMENTATION
================================================================================

10.1 SPRING SECURITY FILTER CHAIN
  - CSRF protection: Disabled (stateless JWT API, no browser session).
  - Session: STATELESS (no HttpSession created or used).
  - Public routes: /api/auth/** (all auth and OTP endpoints).
  - Protected routes: Everything else requires a valid JWT.
  - JwtAuthFilter runs before UsernamePasswordAuthenticationFilter.

10.2 JWT TOKEN DETAILS
  - Algorithm: HMAC-SHA256 (HS256)
  - Secret: Base64-encoded 256-bit key stored in application.properties.
  - Expiry: 86,400,000 ms = 24 hours.
  - Payload: subject = user email.
  - On every protected request, JwtAuthFilter:
      1. Reads "Authorization: Bearer <token>" header.
      2. Extracts username (email) from token.
      3. Loads UserDetails from DB via UserDetailsServiceImpl.
      4. Calls jwtUtil.isTokenValid() to check signature + expiry.
      5. Sets UsernamePasswordAuthenticationToken in SecurityContext.

10.3 PASSWORD SECURITY
  - All passwords stored as BCrypt hashes (salted, irreversible).
  - Spring's PasswordEncoder.encode() used at registration.
  - Spring's AuthenticationManager handles login comparison.
  - Hospital can change password: old password verified before updating.

10.4 CORS POLICY
  - Allowed origins: http://localhost:5173 only.
  - Allowed methods: GET, POST, PUT, DELETE, OPTIONS.
  - Credentials: allowed (for Authorization header).

10.5 INPUT VALIDATION
  - Jakarta Bean Validation annotations on all DTOs
    (@NotBlank, @Email, @NotNull, @Size, etc.)
  - GlobalExceptionHandler (@RestControllerAdvice) catches
    MethodArgumentNotValidException and returns a structured error map.
  - Custom ApiException carries an HttpStatus for clean error responses.

16. HOW THE SYSTEM WORKS — END-TO-END FLOW
================================================================================

STEP 1: DONOR ONBOARDING
  A donor visits Blood Bridge and registers:
    - Fills out personal, medical, and location details.
    - Verifies email via OTP.
    - Account is created; donor receives JWT and lands on Donor Portal.
    - Their lat/lng (from Leaflet map) is stored in the donors table.

STEP 2: HOSPITAL ONBOARDING
  A hospital admin registers:
    - Multi-step form captures all hospital details including GPS location.
    - Verifies email via OTP.
    - Account is created; hospital lands on Hospital Dashboard.

STEP 3: HOSPITAL RAISES A BLOOD REQUEST
  During an emergency, the hospital:
    - Goes to "Send Blood Request" tab.
    - Selects blood group, units, donors needed, urgency level.
    - Enters patient name, notes, and contact phone numbers.
    - Clicks Submit → POST /hospital/blood-requests.

STEP 4: AUTOMATED DONOR MATCHING (happens asynchronously)
  The DonorMatchingService is triggered via @Async:
    - Fetches all available donors with compatible blood groups.
    - Filters by eligibility (age 18-65, weight >=50kg, last donation >=90 days).
    - Computes Haversine distance from hospital to each donor.
    - For NORMAL/URGENT: only donors within 5km (escalation level 1).
    - For CRITICAL: all donors citywide immediately.
    - Creates a DonorNotification record (status=PENDING) for each match.
    - Sends a personalized email to each matched donor.
    - Updates blood_request.sent and blood_request.pending counters.

STEP 5: DONOR RECEIVES NOTIFICATION
  The matched donor:
    - Receives an email alert with blood group, units, urgency, city, distance.
    - Logs into Donor Portal (auto-refresh or manual).
    - Sees the notification in the bell dropdown or Donation Requests tab.
    - Expands the notification card → sees Leaflet map of hospital location.
    - Clicks "Accept" or "Decline".

STEP 6: DONOR ACCEPTS
  On ACCEPT:
    - DonorNotification.status → ACCEPTED, respondedAt set.
    - BloodRequest.accepted incremented, pending decremented.
    - Hospital contact phones (contactPhone1, contactPhone2) are now
      returned in the donor's notification response.
    - Hospital name and address are now visible to the donor.
    - Donor can click the phone numbers to call directly.

STEP 7: HOSPITAL MONITORS THE REQUEST
  On Hospital Dashboard → History → Request Detail View:
    - Sees all notified donors in real time.
    - ACCEPTED donors shown in a highlighted section with full details.
    - Progress bar shows accepted vs target.
    - Escalation level badge shows current radius.
    - Auto-refreshes every 30 seconds.

STEP 8: ESCALATION (if insufficient responses)
  If enough donors don't accept within the time threshold:
    - EscalationService @Scheduled job (runs every 5 min) detects this.
    - Increments escalation level.
    - Calls matchAndNotify() again → notifies newly in-range donors.
    - Already-notified donors are skipped (deduplication check).
    - This repeats until level 3 (citywide) is reached.

STEP 9: REQUEST FULFILLED / CANCELLED
  - Hospital can manually cancel a request at any time.
  - (Future: auto-fulfill when accepted count reaches donorsNeeded)

17. CHALLENGES & DESIGN DECISIONS
================================================================================

CHALLENGE 1: Async Donor Matching Without Blocking API Response
  Problem: Scanning hundreds of donors, computing distances, and sending
           emails could take several seconds. The hospital shouldn't wait.
  Solution: @Async annotation — Spring runs matchAndNotify() in a thread
           pool, the API returns immediately with the created request.

CHALLENGE 2: Avoiding Duplicate Notifications on Escalation
  Problem: When radius widens, same donors must not be re-notified.
  Solution: existsByDonorAndBloodRequest() in DonorNotificationRepository.
           New notifications are only created if no record exists yet.

CHALLENGE 3: LazyInitializationException in getRequestDonors
  Problem: Fetching DonorNotifications then accessing donor.user fields
           outside a transaction caused Hibernate lazy-load errors.
  Solution: JOIN FETCH in the repository query loads all needed
           associations in a single SQL query within one transaction.

CHALLENGE 4: Privacy Without Complex ACL
  Problem: Hospital contact data must be invisible until donor accepts.
  Solution: DonorNotificationResponse DTO conditionally sets
           contactPhone1/contactPhone2/hospitalName/hospitalAddress
           to null unless status == ACCEPTED. Simple, no extra tables.

CHALLENGE 5: OTP Security Without Dedicated Service
  Problem: No Twilio/paid SMS service. OTP must still be secure.
  Solution: Gmail SMTP with @Async for non-blocking delivery.
           SecureRandom for unpredictable 6-digit codes.
           Rate limiting + expiry + attempt limits in OtpService.

CHALLENGE 6: GPS Capture Without Paid APIs
  Problem: Address-to-coordinate conversion (geocoding) requires Google Maps.
  Solution: OpenStreetMap Nominatim (free) for reverse geocoding.
           User pins their location on a Leaflet map → lat/lng stored directly.

CHALLENGE 7: Multi-Step Form State
  Problem: Registration has 4-6 steps with data from each step needed at submit.
  Solution: Each step's data accumulated in a parent formData state object
           and passed down; only submitted to the API at the final step.
